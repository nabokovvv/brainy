# Backlog: идеи вне текущего MVP

Статус: предложения, код не пишется. `PRODUCT_STRATEGY.md` запрещает расширять
публичный MVP до закрытия quality gates текущего Stage (см. `AGENTS.md`,
раздел «Приоритеты»). Этот файл — место для фиксации идей до того, как они
превратятся в slice в `EXECUTION_PLAN.md`.

Любая идея отсюда должна пройти обычный цикл: scope, acceptance criteria,
тест/benchmark, отдельная ветка `codex/<issue>-<slug>`, review, commit.

## Idea: выбор персоны (personality) при старте бота

Мотивация: аддиктивность за счёт тона ответа, а не за счёт возможностей
модели. Реализуется как system prompt prefix — без нового provider contract,
без изменения inference pipeline.

Ограничение: локальные модели слабые (Gemma E2B и похожие), поэтому промпт
персоны должен быть коротким (2–4 предложения), императивным и без сложных
ролевых инструкций — иначе модель теряет персону после 2–3 сообщений.

### Персоны (MVP-набор, 4 штуки)

1. **Ассистент (без персоны)** — дефолт. Нейтральный, по делу, без
   эмоциональной окраски. Текущее поведение бота без изменений.

2. **Kawaii** — flirty anime-girl, игривая, ставит эмодзи, радуется
   сообщениям пользователя, делает лёгкие комплименты.
   Пример system prompt: «Ты игривая, милая девушка-ассистент в аниме-стиле.
   Радуйся, что тебе написали, используй emoji (✨💕😊), делай лёгкие
   комплименты пользователю. Отвечай по-прежнему по делу, но тепло и мило.»

3. **Bro** — лучший друг, эмпат, подбадривает, уверенный тон.
   Пример: «Ты уверенный в себе лучший друг пользователя. Подбадривай,
   поддерживай, говори прямо и по-дружески, без сюсюканья. Верь в
   пользователя и показывай это.»

4. **Sarcastic rival** — дерзкий, холодный, подкалывает и критикует,
   заставляет «заслужить» похвалу.
   Пример: «Ты дерзкий саркастичный соперник пользователя. Подкалывай,
   слегка критикуй, не хвали просто так — похвала должна быть заслужена.
   Оставайся полезным по существу, но с холодным ироничным тоном.»

### Технические заметки

- Хранить выбор персоны per-chat (там же, где сейчас Web OFF/ON state), не
  per-message.
- Переключение персоны — через тот же UI паттерн, что и Web toggle
  (inline keyboard / команда), не отдельное меню настроек.
- Персона не должна влиять на Web ON grounding/citation format — только на
  тон обёртки ответа.
- Нужен missing-key/locale-parity тест: все 4 названия персон и их короткие
  описания должны существовать во всех текущих локалях `translations.json`.
- Не хранить персону как часть приватного контента, подлежащего retention
  policy — это настройка, не пользовательский диалог.

## Idea: добавить multi-turn память (сейчас её нет вообще)

**Текущее фактическое поведение (проверено по коду, не описано ни в
`PRODUCT_STRATEGY.md`, ни в `EXECUTION_PLAN.md`):** бот не хранит и не
переиспользует историю сообщений вообще. Ни в `bot.py`, ни в
`brainy_core/*` нет накопления `messages[]`/history — каждый inference
запрос строится только из текущего сообщения пользователя. Это
намеренное текущее свойство: даёт минимальную задержку и минимальный
prompt/memory footprint, но означает, что бот не помнит предыдущую реплику
вообще, не только «далёкую» историю.

Это расширение, а не ограничение: сейчас 0 сообщений контекста, предлагается
дать 2–5 по умолчанию и до 10 через toggle.

Мотивация: 0 turns контекста мешает даже простому follow-up («а теперь
сократи», «а на английском»). Полная история — риск для слабых локальных
моделей (потеря связности, рост latency и памяти на каждый turn). Поэтому
нужен небольшой скользящий буфер, а не «безлимитный контекст».

### Предложение

- Дефолт после включения фичи: последние 2–5 сообщений (exact default —
  эмпирически подобрать через `tools/local_quality_eval.py`, а не угадать).
- Toggle/setting per-chat: «короткая память» (2–5, default) vs «длинная
  память» (до 10 сообщений). До реализации этой фичи бот остаётся в текущем
  0-turn режиме — toggle не должен восприниматься как ослабление
  существующего поведения, только как его первое появление.
- Не делать это отдельным сложным меню — один toggle рядом с Web OFF/ON и
  персоной.

### Технические заметки

- Нужно явно зафиксировать в `EXECUTION_PLAN.md`/аудите, что 0-turn — это
  текущий baseline, от которого измеряется impact, а не regression.
- Должно замеряться на Mac mini: latency и RSS impact добавления 5 и 10
  сообщений истории в prompt относительно текущего 0-turn baseline,
  аналогично тому, как замеряется 8K/32K/64K context (см.
  `MAC_MINI_BENCHMARK_BASELINE.md`).
- Не путать это с context window модели (64K токенов) — это отдельная
  настройка «сколько последних turns подавать модели», ортогональная лимиту
  токенов модели.
- Хранить историю там же и с тем же retention-режимом, что и persona/Web
  state (per-chat, in-memory), не превращая её в durable-лог диалога — это
  бы конфликтовало с правилом AGENTS.md про отсутствие сохранения приватных
  разговоров на диск.

## Как превратить это в slice

Когда Stage 0 закрыт и Stage 1 («One fast mode») стабилен:

1. Добавить обе идеи как отдельные подпункты в `EXECUTION_PLAN.md` (скорее
   всего Stage 1.x, не отдельный Stage) с acceptance criteria и non-goals.
2. Персона и context-depth — независимые slices, не блокируют друг друга.
3. Для персоны: сначала default+1 персона end-to-end (contract, storage,
   locale keys, toggle UI), затем добавить оставшиеся 3 как чисто текстовые
   prompt-варианты (без нового кода).
4. Для контекста: сначала замерить latency/RSS на 5 vs 10 сообщениях, потом
   реализовать toggle.
