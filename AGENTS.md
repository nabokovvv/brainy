# Brainy: правила для агентов

## Миссия

Brainy — быстрый мультиязычный Telegram-чат: локальная модель при `Web OFF`, явный поиск и проверяемые ссылки при `Web ON`. Главные ограничения — Mac mini M4 с 16 GB unified memory, нулевой денежный бюджет и предсказуемая задержка.

Перед работой прочитай:

1. `docs/PRODUCT_STRATEGY.md` — утверждённое позиционирование и границы MVP.
2. `docs/EXECUTION_PLAN.md` — порядок этапов, quality gates и backlog.
3. Затронутые исходники и тесты. Не полагайся только на README: он устарел.

## Приоритеты

В порядке убывания:

1. Воспроизводимый запуск и отсутствие утечек данных.
2. Корректность и проверяемые источники.
3. Скорость ответа и ограничение памяти.
4. Простота кода и эксплуатации.
5. Новые возможности.

Не расширяй публичный MVP, пока не закрыты quality gates текущего этапа.

## Постоянные архитектурные правила

- Telegram handlers не должны знать форматы конкретных LLM/search-провайдеров.
- Все inference-провайдеры реализуют один типизированный контракт; все search-провайдеры возвращают единый `SearchResult`.
- Все существующие переводы и языки сохраняются. Не удаляй ключи или языковые секции из `translations.json`; при изменении UX обновляй и валидируй все локали.
- Никаких сетевых запросов, скачиваний моделей или тяжёлой инициализации при импорте модулей.
- API-клиенты создаются один раз на lifespan приложения и переиспользуют соединения.
- Конфигурация валидируется при startup условно: нужен только ключ реально включённого провайдера.
- Секреты читаются только из environment/secret store. Не коммить `.env`, ключи, токены или реальные пользовательские данные.
- Не логируй полный prompt, ответ, содержимое страниц или Telegram payload. Используй request id, provider/model, latency, token counts и код ошибки.
- Не сохраняй приватные разговоры, ответы, расшифровки голоса или их Markdown-экспорт на диск. Любое новое хранение пользовательского контента требует явного решения пользователя и отдельной retention policy.
- Обычные тесты не обращаются к Telegram, Ollama, OpenRouter, NVIDIA, search backends или Wikidata. Используй fake providers и записанные HTTP fixtures.
- Новая найденная бесплатная модель не попадает в production автоматически: только `discovered -> eligible -> canary -> active`; при ошибках — `quarantine`.
- Локальная генерация по умолчанию имеет concurrency 1. Увеличение разрешено только после замеров RSS, swap и p95 latency на целевой машине.
- Voice/Whisper — сохранённая продуктовая возможность. Не удаляй и не отключай её без явного запроса; изменения должны сохранять проверенный voice UX и измерять его влияние на память/очередь.
- Бюджет проекта равен нулю. Не включай платные endpoints, автопополнение, chargeable fallback, paid Telegram broadcasts или функции, способные списать деньги/Stars. При исчерпании бесплатной квоты fail closed и переходи на local path.

## Рабочий цикл

1. Проверь `git status` и сохрани чужие изменения.
2. Выбери один незакрытый вертикальный slice из `docs/EXECUTION_PLAN.md`.
3. Сначала зафиксируй воспроизводящий тест или измеримый acceptance criterion.
4. Сделай минимальное изменение без несвязанного рефакторинга.
5. Запусти проверки, относящиеся к изменению, затем полный локальный gate.
6. Проведи отдельный review diff: корректность, async/concurrency, privacy, error paths, память и совместимость конфигурации.
7. Обнови план/документацию, если изменилось поведение или решение.
8. Создай атомарный локальный commit. Не push, merge, deploy и не запускай платные/квотные smoke-тесты без явного разрешения пользователя.

Если проверка не может быть запущена, это не считается успехом: укажи точную причину и оставшийся риск.

## Оркестрация нескольких агентов

- Один orchestrator владеет планом, интеграцией и итоговым решением.
- Делегируй только независимые bounded-задачи: аудит, provider research, реализация отдельного адаптера, тесты или review.
- Один файл одновременно редактирует только один агент. Для параллельной реализации используй отдельные `codex/<task>` branches/worktrees.
- Implementer не утверждает собственную работу: verifier проверяет diff и запускает gates независимо.
- Не создавай агентов ради количества. Если задачи зависят друг от друга или меняют общий интерфейс, выполняй их последовательно.
- Orchestrator интегрирует только green slices и не скрывает разногласия агентов: спор решается тестом, benchmark или ADR.

Роли одного slice:

- `scout`: уточняет scope, риски и acceptance criteria; код не меняет.
- `implementer`: пишет код и unit/contract tests.
- `verifier`: ищет регрессии, проверяет негативные пути и запускает gates.
- `orchestrator`: принимает slice, обновляет roadmap и коммитит/интегрирует.

## Git

- Ветки: `codex/<issue>-<short-slug>`.
- Один commit — одна логическая причина изменения.
- Формат: `fix: ...`, `feat: ...`, `refactor: ...`, `test: ...`, `docs: ...`, `chore: ...`.
- Перед commit проверь staged diff; не добавляй generated `md/`, `charts/`, кэши, модели и локальные базы.
- Не переписывай историю и не используй destructive Git-команды без явного запроса.

## Quality gates

Пока Stage 0 не завершён, минимальный честный baseline:

```bash
PYTHONPYCACHEPREFIX=/tmp/brainy-pycache python3 -m py_compile *.py
```

Stage 0 обязан добавить единые команды для:

```bash
ruff check .
ruff format --check .
pytest -q
```

После их появления они обязательны для каждого code commit. Type checking добавляется после отделения provider contracts от Telegram-кода.

## Definition of Done

Slice готов, только если:

- acceptance criteria покрыты тестом или сохранённым benchmark;
- happy path и важные failure paths проверены;
- нет новых import-time side effects, секретов и plaintext user logs;
- документация и example config соответствуют поведению;
- verifier не оставил P0/P1 замечаний;
- commit содержит только относящиеся к slice изменения.

## Когда остановиться и спросить пользователя

Нужно явное решение для: расходов или привязки карты, публикации/деплоя, push/merge в удалённый репозиторий, удаления пользовательских данных, изменения privacy policy, передачи секретов третьей стороне или необратимой смены продуктового позиционирования.
